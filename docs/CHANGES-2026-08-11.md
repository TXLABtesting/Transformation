## 1. Backend / database changes (action required)

### 1.1 Per-نشاط data model — migration `0011_item_activities`

The biggest functional change: **the child unit of every stream is now a
full record of its own.** In every entry form, each نشاط (ops/strategy) or
خدمة فرعية (services) carries its own القطاع/الإدارة/القسم، الأتمتة،
المصفوفة/أولوية التحول والملاحظات — added via «إضافة نشاط», one complete
section per child.

**DB impact:**
- New nullable column **`items.activities` (JSONB)** — migration
  `0011_item_activities` (`ALTER TABLE "items" ADD COLUMN "activities" JSONB`).
  Zero-risk: additive, no backfill needed.
- Shape: JSON array of `ActivityDetail` (defined in `lib/domain.ts`):
  `{ name, sector, dept, section, isAutomated, automationLevel,
  automationSystem, automationPct, importance, usageIntensity,
  readinessLevel, impactScore, transformScore, outputClarity, riskLevel,
  complexity, transformYes, notes, execBatch, startDate, endDate }` — each
  stream uses its own subset.
- **دفعات الإطلاق are assigned per نشاط**: `execBatch`/`startDate`/`endDate`
  live on each activity, so the أنشطة of one entry may sit in different
  دفعات with their own window-bounded dates. A نشاط with no `execBatch`
  inherits the entry's (legacy rows); the entry's own
  `exec_batch`/`start_date`/`end_date` columns mirror the FIRST activity, so
  batch filters, the detail card, exports and committee cards keep reading a
  single item-level value. No extra column or migration beyond `0011`.
- **Compatibility rule (important):** the legacy flat columns
  (`sub_activities`, `sub_service`, `sector`, `dept`, `section`,
  automation and matrix columns, `transform_priority`…) are **kept and
  mirrored from the FIRST activity** on every save (`mirrorActivities` in
  `lib/domain.ts`); names of all activities are joined into
  `sub_activities` / `sub_service`. Old records without `activities` are
  synthesized into sections on the fly (`itemActivities`). Nothing breaks
  for existing rows, reports, or queries that read the flat columns.
- Derivation: أولوية التحول is computed **per activity** (strategy: matrix
  band — منخفضة→لا; services: priority 4→لا; ops: manual yes/no). The flat
  `transform_priority` mirrors «نعم» if ANY activity is نعم.

**To apply on staging:** `npx prisma migrate deploy` (now runs 0001→0011)
then `npx prisma db seed` as usual. Verified on a fresh PostgreSQL 16:
all migrations apply cleanly, seed unchanged and idempotent.

### 1.2 RBAC seed correction (from the 2026-07-31 pack — re-listed for completeness)

- `entity_representative` no longer holds `items:approve`/`items:reject` —
  **`stream_owner` (رئيس المسار ونائبه) is the sole ent1 approver**, matching
  the client. On an EXISTING database re-running the seed does NOT remove
  already-granted rows — run once:
  ```sql
  DELETE FROM role_permissions rp USING roles r, permissions p
  WHERE rp.role_id = r.id AND rp.permission_id = p.id
    AND r.code = 'entity_representative'
    AND p.code IN ('items:approve','items:reject');
  ```
  (Fresh staging databases seeded from this pack are already correct.)

### 1.3 service_catalog (unchanged since 2026-07-31, listed as context)

- `service_catalog` table + `GET /api/svc-catalog` (entity-scoped) —
  migration `0010`. No further change.

## 2. Bulk upload / Excel semantics (behavioral change, no DB action)

- **Template**: one row per نشاط/خدمة فرعية. The main entry's cells
  (العملية الرئيسية / المهمة / الخدمة + التصنيف/المحور) repeat on each of
  its rows. Ops/strategy columns renamed: «اسم النشاط الفرعي» / «اسم النشاط».
- **Import**: consecutive rows sharing the same header identity
  (ops: title+التصنيف+نوع الدعم — strategy: المحور+title — services: title)
  fold into ONE entry with `activities[]`. Row values are normalized like
  the form (conditional fields cleared, automation clamped كلياً=100/جزئياً≤95,
  أولوية التحول derived) and incomplete rows keep importing as
  «بيانات ناقصة» drafts, with the missing fields named per نشاط.
- **Excel report** (تحميل التقرير): also one row per نشاط with per-activity
  values and its own أولوية الاختيار — report and template are now the
  same shape.

## 3. Calculations (client logic — no DB action)

- KPI strips count **activities**, not parent entries (إجمالي الأنشطة،
  القابلة للتحول، المستهدف تحويلها، and the priority boxes in strategy/
  services).
- القابلة للتحول / المستهدف تحويلها on the committee/recap cards: an entry
  qualifies when ANY of its activities qualifies.
- أولوية الاختيار in the list and دفعات tables shows the distinct set
  across activities (e.g. «الأولوية 1، 2»).
- **Filter fix**: the per-stream dropdown filters (التصنيف، نوع عملية
  الدعم، القطاع، الخدمة، المحور، الأولوية) were not applied to the list
  table — now enforced; priority/sector filters match if ANY activity
  matches.

# Addendum — 2026-08-12

Follow-up round after the first staging build. **No schema migration is
required for this addendum** — `0001…0011` remain the full migration set.

## A. Rejection is now a first-class status

`items.returned_type` (already present, values `info` | `reject`) is now
surfaced end to end:

| Where | Behaviour |
|---|---|
| قائمة الحصر card/table | red chip «تم الرفض» (`#C0303B` on `#FDECEE`) instead of the amber «للتعديل» |
| دفعات الإطلاق table | same chip — the row no longer falls back to the raw workflow label |
| Detail drawer | banner label switches to «سبب الرفض من رئيس المسار» and prints `returned_note` |
| معيار الحالة filter | new option «تم الرفض»; «للتعديل» now matches `returned_type = 'info'` only |

A rejected entry still returns to the coordinator in `draft` so it can be
corrected and re-submitted — only its presentation changed. Backend rule:
`status_label = 'تم الرفض' WHEN returned_type = 'reject'`.

## B. دفعات الإطلاق — coordinator arrangement + head review

Placements are stored per نشاط in `items.activities[].exec_batch`
(jsonb, added in `0011`). An **explicit empty string** means «removed from
its دفعة» and must NOT inherit the parent entry's batch; only an absent
key inherits. Endpoints affected:

- `PATCH /api/items/:id/activities/:idx/batch` — move (`{batch}`) or
  remove (`{batch: ""}`). Placement alone does not change `workflow_state`.
- `POST /api/items/batch-drafts/:streamId/submit` — sends every `draft`
  entry of that stream that has at least one placed نشاط to `ent1`.
  Incomplete entries are refused with the missing-field list.
- رئيس المسار can approve / return-for-edit / reject directly from the
  batches table; these reuse the existing approve, req-info and reject
  endpoints on the parent entry.

## C. دليل الخدمات — fallback when the entity is not in the catalog

`service_catalog` (migration `0010`, 1855 rows / 47 entities) is still
scoped strictly to the signed-in coordinator's entity. Two of the pilot
entities — including **وزارة شؤون مجلس الوزراء** — are absent from the two
source workbooks, which left the dropdowns empty. New behaviour:

1. entity present in `service_catalog` → its services only (unchanged);
2. entity absent → the full federal directory is offered, with the notice
   «جهتك غير مدرجة في دليل الخدمات المرفوع — تُعرض القائمة الاتحادية الكاملة»;
3. either way a final option «أخرى — إدخال يدوي» switches to free text.

`GET /api/svc-catalog` should mirror this: return `{ services }` for the
session entity, and when that entity has no rows return the union of all
entities plus `{ scoped: false }` so the UI can show the notice. The
downloaded Excel template uses the same source for its dropdown lists.

> load it into `service_catalog` and the fallback disappears on its own —
> no code change needed.
